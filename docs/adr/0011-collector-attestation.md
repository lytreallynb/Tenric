# ADR-0011: The verdict can require a signed record from a collector the operator trusts

Status: implemented and tested; awaiting owner approval. Date: 2026-11-27.

**Context.** Every `provenance` field in a run directory is written by whoever wrote the run directory. `provenance: "collector"` was a mark, not proof (trust model, section 2). The control group of the runtime evaluation showed the consequence: an agent with no runtime around it wrote its own run directory, called every section `collector`, and under contracts 0.1.0 to 0.3.0 nothing distinguished it from a run the collector produced. ADR-0009 and ADR-0010 (runtime work) give the runtime a key and a sandbox for the agent; what was missing was a verifier that asks for the runtime's signature and refuses without it.

**Decision.**

- A collector signs a statement about the run it collected and writes it to `tenric/attestation.json` in the run directory: `{ attestation_schema: "0.1.0", statement, signature: { alg: "ed25519", key_id, public_key, value } }`. `key_id` is the SHA-256 of the public key's SPKI DER bytes. The signature covers the canonical bytes of `statement`: keys sorted at every depth, no whitespace, floats refused (they have no single text form across languages).
- The statement names at least `type: "tenric.collector-record"`, `version: "0.1.0"`, `collector_id`, the artifact's SHA-256, the source revision and the contract (id, version, SHA-256). The runtime adds the run, the plan, the backend and the isolation it used; the verifier records them and does not judge them.
- The operator of the verifier lists the collectors it trusts in a collectors file: `{ id, key_id, public_key, custody, establishes[], revoked? }`. `custody` says in words where the private key lives. `establishes` lists the capabilities the operator is willing to say that collector provides (for example `independent-collector`). The default file, `spec/collectors/registry.json`, is empty: this repository trusts nobody until an operator says so. `tenric verify --collectors <file>` points at another one. An invalid file gives no verdict (exit 2).
- Contract 0.4.0 adds mandatory machine requirement R-012, check kind `collector-attestation`. It fails when the attestation is missing, is signed by a key not in the collectors file or a revoked one, does not verify, names another collector, another artifact digest, another revision or another contract. Contracts 0.1.0 to 0.3.0 are unchanged and do not require it.
- Under every contract, the verifier checks the attestation anyway and says the result: the statement ends `; evidence collected by <id> (attested)` or `; collector not attested`, and the record has `collector` (attested, id, key id, custody, isolation, problems) and `collectors` (path and SHA-256 of the file used). `capabilities.established` is the trusted entry's `establishes` when attested, and empty otherwise.
- New CLI commands for operators and tests: `tenric collector-key` (writes an Ed25519 key with mode 0600 and the matching collectors-file entry, refuses to overwrite) and `tenric attest` (signs the minimal statement for a run directory).

**What a pass of R-012 means.** Someone holding a private key that this verifier's operator listed signed a statement that names exactly this artifact, revision and contract. It moves the trust question from "who wrote this file" to "who holds that key and what does that collector actually isolate". It does not say the collector was honest or that its sandbox held; that is what `custody` and `establishes` record, and they are the operator's statements, not the verifier's findings.

**Known limits.** A key on the same machine and user as the agent can be read by the agent unless the runtime's sandbox prevents it (ADR-0010 is where that is claimed). There is no key rotation beyond `revoked`, no timestamping, and no transparency log (Q16, Q19). A run signed for contract 0.3.0 does not count under 0.4.0: the statement names the contract, so a re-signature is needed.

**Alternatives.** Trusting a CI job's identity (OIDC token from GitHub): stronger custody, ties the verifier to one provider, and is still available later as another kind of collector entry. Sigstore or in-toto: the right shape for distribution, a new dependency without a demonstrated need yet (hard rule 6); the statement layout is close enough to move later. An HMAC shared secret: the verifier would hold a key that can forge.

**Reverse if** the owner decides a verdict must not depend on a list kept by the operator, or a standard attestation format is adopted.
