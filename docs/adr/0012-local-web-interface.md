# ADR-0012: A local web interface that displays and never decides

Status: implemented and tested; awaiting owner approval. Date: 2026-11-27.

**Context.** Until now the only way to see a verdict was the command line. `docs/phase-1-plan.md` listed "any UI" as explicitly not in Phase 1. On 2026-11-27 the owner asked for the interfaces to be built now, in parallel with the trust-boundary and runtime work. This record covers what was built under that instruction and the constraints it was built to. It was first numbered 0009 and was renumbered 0012 when the runtime work took 0009 and 0010 and collector attestation took 0011.

**Decision.**

- `npm run ui` starts a server on the loopback interface (`ui/server/`, Node's built-in `http`, TypeScript run by type stripping) that serves the front end built from `ui/web/` (see "Components" below). The server itself adds no dependency.
- The interface displays; it does not decide. Every verdict is the record issued by `verify()` in `src/verify.ts`, reached through one file, `ui/server/core.ts`. Verification with re-execution runs the verifier's own command line as a separate process, because it takes seconds to minutes, and reads the record from its output. A contract file the registry does not list gets "no verdict issued", as on the command line. The verdict wording is the command line's, and a test compares the two on the real runs that `scripts/verify.sh` produces.
- It stores nothing (ADR-0004 stands). Verdicts are recomputed from the files on disk on every request. The list of processes started from the interface is held in memory and says so.
- Anything a slice has not delivered is shown as "not yet available", found by looking for the file or command that would provide it. Nothing is rendered from sample data. Fixtures are listed, labelled as fixtures, and never verified.
- Capabilities a contract requires are shown as "not established", which is what the verdict record says.
- Provenance is shown as "declared provenance". The label is a string in `artifact.json`; the interface says so on the page that separates evidence from claims.
- It can start a run: the Phase 0 baseline collector, or any backend the runtime lists (`node src/tenric.ts backends --json`) with any task under `tasks/` or `fixtures/tasks/`. Runtime runs are started through the runtime's command line as a separate process and followed by reading `tenric/events.jsonl`; the interface does not import the runtime. It can also compile a task without running it.
- For a run the runtime made, it shows the compiled plan, the lifecycle events with their source, the backend's self-report labelled as a claim, the re-execution comparison and the verdict record the runtime stored. That stored record is shown as a stored file. The Verdict tab still recomputes: it verifies against the run's own `workspace/` repository, under the contract the run was compiled against, and with the run's own re-execution task when asked. A test checks that this reaches the statement the runtime recorded.
- Text is in English and Chinese. The verifier's vocabulary (`pass`, `fail`, `error`, `not_run`, `accepted`, `rejected`, `inconclusive`, provenance values) is never translated.

**Why a server and not static pages.** Verdicts must be computed by the verifier at the moment of viewing, against the files as they are, and digests on disk must be compared with digests on record. A static export would be a copy of a verdict, which is exactly what the trust model warns about.

**Trust.** The interface is not part of the trusted computing base and adds nothing to it. It runs as the same user in the same working tree as the producer, so it is advisory against a deliberate producer in the same way the command line is (`docs/trust-model.md`). Because it can start processes, it refuses requests whose `Host` is not a loopback name, state-changing requests from another origin or without a JSON content type, run ids that are not a single safe path segment, and file paths that resolve outside a run directory. Run output is produced by untrusted code: it is never served as HTML and the front end never parses it as HTML.

**Appearance.** The first front end was hand-written ES modules and CSS in `ui/public/`, restyled twice on 2026-11-27 at the owner's request. It was replaced the same day by the component-based front end below. Every status shown is still a word the verifier or the runtime recorded. The chosen language and theme are kept in the browser's local storage; nothing else is stored.

**Components (2026-11-27).** The owner judged the hand-styled front end not good enough and asked for it to be built on components. This reverses the "no framework, no build step" choice for the front end only, and is the demonstrated use that hard rule 6 asks for: the same eight screens, rebuilt on a maintained component library, look and behave like a finished product, which three rounds of hand-written CSS did not achieve.

- The front end lives in `ui/web/` with its own `package.json` and `package-lock.json`, so the repository's own dependencies, `npm ci` and `npm run verify` are unchanged. Every version is exact. Runtime packages: `react` and `react-dom` 19.3.1; `radix-ui` 1.8.1 (accessible primitives under the shadcn/ui components); `class-variance-authority` 0.7.1, `clsx` 2.1.1 and `tailwind-merge` 3.7.0 (the shadcn/ui styling helpers); `lucide-react` 1.71.0 (icons); `@tanstack/react-table` 8.21.3 (sortable, selectable tables); `recharts` 3.10.1 (charts); `@fontsource-variable/geist` and `geist-mono` 5.3.0 (fonts, served locally). Build only: `vite` 8.3.8, `@vitejs/plugin-react` 6.3.0, `tailwindcss` and `@tailwindcss/vite` 4.3.5, `tw-animate-css` 1.4.0.
- The shadcn/ui components are copied into `ui/web/src/components/ui/` in the library's own form and default theme, as that library intends; they are not restyled. The only colours added are three for verdicts (success, warning and the library's destructive).
- `npm run ui` (`ui/start.ts`) runs `npm ci` in `ui/web/` when its lockfile changed, builds with Vite when any source is newer than the last build, then starts the server. Without a build the server answers the page with 503 and the command to run, rather than an empty page. The build output (`ui/web/dist/`) is not committed.
- The content security policy is unchanged (`default-src 'self'`, no inline script or style). React sets styles through the DOM, which that policy allows. A test checks that the page's sources contain no inline script or style and never parse a string as HTML, and that every front-end version is exact.

**Cancelling, review and the trust boundary.** Added on 2026-11-27. `POST /api/jobs/<id>/cancel` sends SIGTERM to a running job. The runtime handles that signal itself and records the run as `cancelled`; it is never sent SIGKILL, because that would leave `run.json` unfinished. The baseline collector, which does not handle signals, runs in its own process group and is killed if it is still running after a grace period. Each run's page has a human-review section that lists what a person would have to decide and states that recording a decision is not built (Q10), and a trust-boundary section that shows, from the run's own records, the capabilities the contract requires, the isolation and the collector attestation the runtime recorded (keys `isolation` and `attestation` in `tenric/run.json`, agreed with the runtime work; absent today and shown as not yet available), the backend's own sandbox declaration, and the runtime's integrity check of trusted files. Nothing in either section is inferred. Since the runtime signs its collector record, the verdict depends on which collectors file the verifier trusts. The interface verifies under the repository's file (`spec/collectors/registry.json`, the command line's default) unless the reader picks the file that the runtime's stored verdict used (`collectors: "recorded"`); it accepts no other path from a request.

**What is not covered.** No authentication: anyone who can reach the loopback port as a local user can start or cancel a run. No human-review recording (open question Q10 is unanswered). Starting an agent backend from the interface goes through the same code path as the script backend, which is tested; the agent path itself is not covered by an automated test, because it needs a model. The front end has no automated tests of its own beyond the API tests, a string-table check and the source checks above; it was exercised in a headless browser at desktop and phone widths in both themes. `npm run verify` does not build the front end, so a front-end build error is caught by `npm run ui`, not by verify.

**Alternatives.** Keeping hand-written CSS: tried three times, and the owner rejected the result. Another component library (MUI, Ant Design, Mantine): each brings its own look and a larger runtime; shadcn/ui puts the component source in this repository, where it can be read and pinned. A component library loaded from a CDN: the interface must work offline and its policy loads nothing from elsewhere. A static report generator: see above. A terminal interface: no figures, and no side-by-side comparison worth having. A Python server: the verifier is TypeScript, and calling it across a process boundary for every page would be slower and no more independent.

**Reverse if** the interface starts to hold state that the verifier does not, or if any screen needs to compute a status itself. Either would mean it has stopped displaying and started deciding.
