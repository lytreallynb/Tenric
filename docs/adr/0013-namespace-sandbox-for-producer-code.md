# ADR-0013: Producer code runs in a Linux namespace sandbox, and the runtime signs only runs it confined

Status: implemented and tested; awaiting owner approval. Date: 2026-11-27.

**Context.** The runtime executed code written by a model on the host, as the runtime's user: the agent's own tool calls through the Claude Code CLI, and the experiment it wrote. The runtime noticed changes to the contract, schema and its own source after the fact (ADR-0009) and prevented nothing. ADR-0011 lets a verdict require a record signed by a collector the operator trusts. A signature is worth something only if the code being judged cannot reach the key, so the key and the sandbox are one decision.

**Decision.**

- `src/runtime/sandbox.ts` and `src/runtime/sandbox.sh` build a sandbox from Linux user, mount and PID namespaces, plus an empty network namespace when network is off. The new root is an empty tmpfs that holds the system directories (`/usr`, `/bin`, `/lib*`, `/etc`) read-only, the paths the caller lists read-only or writable at their own absolute paths, and a private `/tmp`, `/proc`, `/dev/shm` and a few device nodes. The command runs as an unprivileged user in a nested user namespace with `no_new_privs`, which locks every mount: it cannot remount a read-only path writable or unmount one. It uses only util-linux (`unshare`, `setpriv`), which every Linux distribution ships; no new dependency.
- The agent backend runs in it with the workspace writable; the Tenric repository, its Python environment, the CLI's real installation and certificate bundles read-only; network on, because the CLI must reach its model. Configuration the CLI needs (for example credentials in a config directory) is exposed only when the operator names it in `CLAUDE_CONFIG_DIR` or `TENRIC_SANDBOX_READONLY`.
- The experiment runs in it with network off, the workspace read-only, and an empty directory of its own as the only writable path. The collector moves the files into the run directory afterwards, so the experiment never sees the run directory or the records in it. The verifier's re-execution of a runtime run goes through `tenric collect` and therefore through the same sandbox.
- The runtime's Ed25519 key lives in `~/.config/tenric` (or `TENRIC_KEY_DIR`). `sandboxed()` throws if a spec would expose it, rather than exposing it. On first use the runtime writes `collectors.json` next to the key and passes it to `verify()`; the repository's own collectors file stays empty.
- The runtime signs the collector record (ADR-0011's format, through the verifier's `signStatement`) only when the experiment ran in an enforced sandbox without network, and, for an agent backend, the agent did too. Otherwise `run.json` says why in `attestation_refused`.
- Where no sandbox can be built (macOS, Windows, a kernel without unprivileged user namespaces, or `TENRIC_SANDBOX=off`), an agent backend is refused unless the caller passes `allowUnsandboxed`; such a run is recorded as unconfined and never signed. Script backends still run, unsigned.

**What it does not give.** No limit on CPU, memory, disk or time other than the runtime's timeouts. No restriction on the agent's network: it can reach any host and any service on the host's network, including abstract Unix sockets. The sandboxed user is the runtime's user on the host, so the files it is shown are readable regardless of their permissions; what protects the rest is that it is not shown. It does not protect against kernel vulnerabilities. The configuration directory the operator exposes may hold the agent's own credentials, which the agent can then read. Group B's agent-written `collect.py`, which the verifier re-executes directly, is not sandboxed by this (Q17).

**Alternatives.** bubblewrap: the same mechanism with better defaults, but a new system dependency and not installable on the development machine. Docker or Podman: a daemon and images to manage, much more than the need. gVisor or a VM: stronger isolation, a large dependency and a very different deployment. Claude Code's own sandbox settings: they rely on bubblewrap on Linux and cover only that one CLI, not the experiment.

**Reverse if** a stronger isolation (a VM per run, or a remote runner with its own key custody) becomes available, or the owner decides that model-written code must never run on the operator's machine at all.
